# AI 内容生产平台需求文档

文档版本：V0.1  
状态：已评审通过，进入技术设计  
适用仓库：`lxxlx2/ai_video_product`  
首个音乐项目：《后来没有故乡》

## 1. 背景

`ai_video_product` 已经同时承载视频、音乐和后续可能出现的其他 AI 生成产物。随着本地模型、参考素材、生成脚本、候选文件、日志和 Git 历史逐渐增多，当前按单个任务临时推进的方式已经不能满足长期维护要求。

主要问题包括：

1. 视频、音乐、脚本、配置和输出文件缺少统一分类。
2. UI 操作和人工复制参数难以复现，也不适合后续 Codex 自动执行。
3. 中间文件、模型缓存、失败产物容易污染磁盘和 Git。
4. 生成参数、提示词、歌词、参考素材、日志和最终文件缺少统一关联。
5. AI 生成存在随机性，需要标准候选、审核、批准和回滚流程。
6. 大型媒体文件需要明确区分 Git、Git LFS 和本地私有存储。
7. 后续目标是由 Codex 接管执行，用户只参与创作决策和最终审核。

## 2. 产品定位

`ai_video_product` 定义为个人 AI 数字内容生产与归档仓库。

仓库承担两项职责：

```text
生产流程可复现
+
最终产物可追踪
```

仓库主要承载：

```text
视频产品
音乐/音频产品
其他 AI 产品
共享生产能力
需求与技术文档
结构化任务配置
审核记录
最终正式产物
```

模型权重、缓存、私有参考素材和大量临时中间文件原则上不进入 Git。

## 3. 总体目标

最终工作流：

```text
用户提出创作需求
        ↓
AI 整理需求与方案
        ↓
结构化任务配置
        ↓
自动执行本地模型或外部 AI 工具
        ↓
自动保存产物、参数和日志
        ↓
生成可审核候选
        ↓
用户审核
        ↓
继续迭代或批准
        ↓
批准版本正式归档
        ↓
Git / Git LFS 同步
        ↓
安全清理中间产物
```

当前阶段保留“ChatGPT 配置，用户执行一条命令”的人工执行点。

目标阶段由 Codex 接管执行，用户最终只需要：

1. 表达创作需求和修改意见。
2. 审核候选结果。

## 5. 角色与职责

### 5.1 用户

负责：

```text
提出创作需求
决定创作方向
试听或观看候选
提出修改意见
确认最终版本
```

用户原则上无需直接维护模型参数和底层调用细节。

### 5.2 ChatGPT

当前过渡阶段负责：

```text
需求澄清
歌词、脚本、提示词创作
方案设计
参数设计
候选分析
维护任务配置
维护产品文档
检查 Git 运行结果
规划下一轮实验
```

### 5.3 Codex

目标阶段负责：

```text
读取需求
维护配置
执行命令
调用模型
检查运行状态
处理错误
生成候选
整理日志
提交 Git
执行最终固化和安全清理
```

用户确认前，Codex 不得自行把候选设为最终版本。

## 6. 标准产品生命周期

每个产品统一采用以下生命周期：

```text
需求
  ↓
方案
  ↓
结构化配置
  ↓
执行
  ↓
候选审核
  ↓
迭代
  ↓
最终批准
  ↓
归档
  ↓
清理
```

### 6.1 需求阶段

至少记录：

```text
作品目标
主题
风格
内容
参考素材
长度
语言
输出格式
质量要求
特殊限制
```

### 6.2 方案阶段

至少形成：

```text
内容结构
提示词或脚本
模型选择
参考素材使用方式
候选策略
关键生成参数
```

### 6.3 结构化配置

所有影响结果的关键条件必须转为机器可读取配置，禁止长期依赖 UI 隐含状态。

至少包含：

```text
模型
任务类型
提示词
歌词或脚本
参考素材
时长
种子策略
关键生成参数
输出格式
任务版本
```

### 6.4 执行阶段

每次运行必须自动记录：

```text
run_id
开始时间
结束时间
运行状态
代码版本
模型版本
请求参数
日志
错误信息
产物路径
SHA-256
```

### 6.5 候选审核

每次生成形成一个独立 Run。审核材料至少包含：

```text
试听或预览文件
本次配置
结果摘要
运行日志
候选 SHA-256
```

用户可以：通过、拒绝、要求修改、要求重新生成。

### 6.6 最终批准

用户批准必须绑定：

```text
run_id
+
candidate_sha256
```

避免批准错文件。

## 8. 《后来没有故乡》项目目标

### 8.1 当前目标

以现有 Suno 满意版本为参考，通过本地模型获得可接受的近似版本。

重点关注：

```text
情绪
男声音色方向
旋律走向
节奏
调性
段落结构
配器
动态发展
歌词演唱方式
```

不要求数字级完全一致。

### 8.2 长期目标

在不依赖 Suno 的情况下形成：

```text
讨论主题
  ↓
生成歌词
  ↓
生成 Style
  ↓
AI 作曲
  ↓
AI 编曲
  ↓
AI 演唱
  ↓

```

## 9. 参考素材需求

参考素材必须区分：

```text
原始参考文件
工作参考文件
```

例如当前音乐项目：

```text
原始：后来没有故乡.m4a
工作：后来没有故乡.reference-48k.wav
```

必须分别记录 SHA-256，明确 API 实际读取哪一个文件。

涉及版权、隐私或大体积的参考文件允许只保留本地，Git 仅记录文件名、格式、时长、SHA-256、生成方式和用途。

## 10. 分析需求

参考作品进入生成流程前，应优先完成结构化分析。

音乐分析至少包含：

```text
BPM
Key
拍号
时长
语言
曲风
结构
人声类型
配器
动态
模型可提取的语义信息
```

模型分析结果允许人工修正，并应保留原始分析与修正后的生产参数。

## 11. 候选与审核文件需求

每个 Run 至少包含：

```text
request.json
result.json
run.json
runner.log
server.log
candidate
review
```

完整高质量候选默认保存本地私有运行目录。

Git 中保存轻量审核版本。例如音乐：

```text
本地：candidate.wav
Git：review.mp3
```

最终批准后再把准确候选固化为 `output/final.*`。

## 12. Git 与 Git LFS 需求

Git 主要承担：

```text
版本管理
配置管理
文档管理
审核记录
最终产物管理
跨 Agent 状态同步
```

媒体最终文件使用 Git LFS。

建议纳入 LFS 的格式：

```text
wav flac mp3 m4a aac ogg mp4 mov mkv
```

禁止提交：

```text
模型权重
模型下载缓存
密钥、cookie、token、.env
大量临时实验文件
可重新生成的大型缓存
```

## 13. 本地文件需求

本地 AI 文件统一放在 `~/AI/` 下，逻辑上划分：

```text
runtime/   模型和运行环境
private/   私有参考和完整候选
logs/      服务日志
run/       PID 和服务状态
cache/     可清理缓存
```

具体目录由技术设计定义。

## 14. 自动化阶段

### 阶段一

```text
ChatGPT 决定配置
用户执行一条命令
脚本自动完成其余流程
```

用户无需手工填写 UI、复制参数、寻找结果、转码、整理日志或手工选择 Git 文件。

### 阶段二

```text
ChatGPT / 用户确认需求
Codex 修改结构化任务
Codex 执行
Codex 检查
Codex push Git
用户审核
```

### 阶段三

```text
自然语言需求
  ↓
Codex 自动建立任务
  ↓
AI 创作
  ↓
自动多候选和技术检查
  ↓
用户选择
  ↓
正式发布
```

## 15. 一键执行需求

每个项目最终需要一个稳定入口，例如：

```text
make generate
```

或等价的一条命令。

入口需要自动完成：

```text
检查 Git 状态
检查任务配置
检查素材及 SHA
检查模型服务
启动或复用服务
提交任务
轮询任务
收集结果
技术验证
生成审核文件
提交 Git
输出 Run ID
```

## 16. 错误处理需求

错误必须有明确阶段码，例如：

```text
PRECHECK_FAILED
MODEL_INIT_FAILED
REFERENCE_INVALID
API_SUBMIT_FAILED
GENERATION_FAILED
RESULT_INVALID
GIT_PUBLISH_FAILED
```

失败后必须尽量保留请求和日志，并允许安全重试。

一次失败不得导致：

```text
删除有效模型
覆盖最终文件
污染其他产品 Git 状态
重复下载大模型
丢失已生成候选
```

## 17. 模型服务 READY 定义

模型服务状态必须区分：

```text
HTTP 服务可访问
DiT 已加载
LM 已加载
指定模型版本正确
可以接受任务
```

仅端口可访问不得视为 READY。

## 18. 可复现性需求

每个正式候选应尽量保存：

```text
代码版本
模型名称和版本
提示词
歌词或脚本
生成参数
seed
参考素材 SHA
任务类型
生成时间
```

对于存在非确定性的模型，只要求最大程度可复现。

## 19. 最终产物要求

音乐至少保留：

```text
output/final.wav
```

按需要可增加：

```text
final.mp3
cover.png
lyrics.txt
metadata.json
```

视频至少保留：

```text
output/final.mp4
```

## 20. 清理策略

永久保留：

```text
最终产物
最终配置
批准记录
核心文档
```

审核期间保留：

```text
当前候选
近期必要候选
review 文件
对应日志
```

可清理：

```text
失败任务的大型中间文件
临时 WAV / MP3 / 视频
模型下载残片
转码缓存
过期实验
重复文件
```

最终结果未完成远端验证前不得清理已批准源候选。

## 21. 仓库信息架构要求

目标结构：

```text
ai_video_product/
├── products/
│   ├── video/
│   ├── music/
│   └── other/
├── shared/
│   ├── video/
│   ├── music/
│   └── common/
└── docs/
```

产品放 `products/`，通用能力放 `shared/`，仓库级规范和设计放 `docs/`。

现有历史项目逐步迁移，迁移过程不得破坏有效产物和正在进行的本地工作。

```text

```

复杂产品可增加：

```text
design.md
operations.md
progress.md
```

```text
docs/PRODUCT_REQUIREMENTS.md
docs/TECHNICAL_DESIGN.md

docs/PRODUCT_WORKFLOW.md
```

默认使用中文，代码、API 字段和路径保持英文。

## 23. 当前成功指标

第一阶段完成标准：

```text
一条命令可以执行音乐任务
自动调用 ACE-Step
自动获得结果
自动生成 review
自动保存请求、日志和 SHA
自动提交 Git
ChatGPT 可以从 Git 检查运行结果
用户可以直接试听

```

第二阶段完成标准：Codex 可以独立执行以上流程。

第三阶段完成标准：从自然语言需求到候选作品，主要生产流程由 Agent 自动完成。

## 26. 产品原则

长期遵循：

```text
自然语言负责表达需求
结构化配置负责执行
脚本负责确定性流程
模型负责生成
Git 负责状态同步和版本历史
本地 private 负责大文件和敏感素材
用户负责最终审批
Codex 最终负责执行
```

同时坚持：

```text
先验证短任务，再运行昂贵长任务
```

任何 5 分钟级音乐、长视频或高成本任务，在关键参数尚未通过短任务验证前，不直接进入完整生成。

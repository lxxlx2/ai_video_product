
源 M4A 与 ffmpeg 派生出的 PCM WAV 字节内容不同，因此 SHA-256 必然不同。源文件 SHA 只用于 `prepare_reference.sh` 验证输入来源，后续 ACE-Step API 分析和生成实际读取工作 WAV，因此必须校验工作 WAV SHA。

2026-09-12 首次 `run_reference_analysis.sh` 验证暴露了这里的配置错误：job 把源 M4A SHA 当成工作 WAV SHA，脚本正确拒绝继续。随后修复配置时又人工多录入了一个 `9`，产生了 65 位伪 SHA：

```text
错误: 288edd5197a7535d9dadfac27dc1aea4699999e16dc6dfeaf1291cc882afd6775
正确: 288edd5197a7535d9dadfac27dc1aea469999e16dc6dfeaf1291cc882afd6775
```

第二次运行再次被校验拦截。现已修正 `metadata/reference.json`、`jobs/reference-analysis.json`、`jobs/current.json`。同时 `reference_analysis.py` 新增 SHA-256 格式校验，配置值必须严格为 64 个十六进制字符，避免以后把长度错误误判成普通文件不一致。
